1. Must be science-backed. Every physics-driven simulation should include reference to reputable peer-reviewed literature
2. Do not over-engineer and aim for simplicity in each logic workflow. If a simpler solution exists, use it.
3. Code should be modular and reusable. Avoid hardcoding values and logic that could be easily abstracted into functions or classes.
4. Do not comment code that is self-explanatory. Instead, focus on commenting complex logic or decisions that may not be immediately clear to other developers.
5. Same for docstring -- keep is simple
6. Aim for a central config.py file that contains all the parameters and settings for the simulation. This will make it easier to manage and update configurations without having to search through the codebase.
7. Use version control and commit often with clear (and short) messages.
8. !IMPORTANT: ask the user often for every design choices, and, for each, present pros and cons of each option. Do not make assumptions about what the user wants without asking them first.
9. Validate predictions against ground truth - Ensures model reliability
10. !IMPORTANT: keep replies to the user of under 100 words per reply. This will encourage concise communication and make it easier for the user to understand and respond to the information provided. If more information is needed, the user can always ask follow-up questions.
11. Do not output any additional e.g., markdown files in the project directory. Keeep all organized.
12. Do not be superficial, aiming to have scientifically rigorous and detailed explanations for all design choices, assumptions, and methodologies used in the simulation. This will ensure that the simulation is based on sound scientific principles and can be trusted by users and other researchers in the field.
